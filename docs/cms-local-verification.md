## 3. Importer — no-DB dry-run by default

From the same repository root, with an operator-selected private read-only **sanitized** NDJSON file:


### Exact CLI parser — no invented options

The [parser](../scripts/import-sanity-ndjson.ts) accepts only:

| Option | Behavior |
| --- | --- |
| `--file <path>` | Required source file, no implicit backup/default path. |
| `--dataset-id <uuid>` | Required explicit target scope; syntax-only in dry-run. |
| `--actor-id <uuid>` | Required explicit local operator actor; syntax-only in dry-run, live policy on apply. Not an HTTP authentication mechanism. |
| `--dry-run` | Explicit no-DB planning. Mutually exclusive with `--apply`. |

Duplicate options, unknown options, missing values, combined dry-run/apply and confirmation without apply are errors. Options use separate values, not `--name=value`. ## 4. Explicit apply — only a named disposable local database

**DANGER: apply writes immutable CMS history/receipts and audit rows. It is not a migration/setup/cleanup command. Do not run it against production, shared DBs, generic `postgres`, or forwarded/tunneled targets. This docs task does not authorize or execute apply.** Use only after separate local setup approval and an inspected dry-run on sanitized data; no dataset provisioning UI exists.

The [target gate](../apps/web/src/lib/cms/import/local-database.ts) requires all of:

- `NODE_ENV` is not the exact string `production`.
- Explicit `DATABASE_NAME` matching **`^cms_import_test_[a-z0-9_]+$`**, e.g. `cms_import_test_review_20261019`; uppercase names, empty suffix and generic names are rejected.
- Explicit `DATABASE_URL` with `postgres:` or `postgresql:` protocol; host exactly **`127.0.0.1` or `[::1]`** (not `localhost`); decoded path exactly `/<DATABASE_NAME>`; no fragment. Any query entries must be exactly `schema=public`; no query is also accepted. No URL option overrides/production defaults are provided.
- The [apply service](../apps/web/src/lib/cms/import/service.ts) checks live `current_database()` equals the name and `inet_server_addr()` is loopback. **These checks cannot prove absence of an SSH tunnel/proxy**; independently verify cluster/data-directory ownership and disposal scope. An unknown target is a stop condition.
- Both `JONGO_CMS_ENABLED=true` and `JONGO_CMS_WRITES_ENABLED=true`; compatible CMS tables/client; actual live dataset/tenant/actor plus actual persisted owner entitlement, freshly authorized and locked using the native write policy. Dataset confirmation matches exactly. No synthetic paid/financial/admin bypass.

Configure the two DB variables privately in that isolated process through an approved secret channel; this guide deliberately supplies no credential-bearing URL or migration SQL. Once every gate and separate approval is satisfied, the actual command form is:

```text
npm run cms:import:sanity -- --file <path> --dataset-id <uuid> --actor-id <uuid> --apply --confirm-dataset <same-dataset-uuid>
```

Apply does not load dotenv. Its URL gate runs before importing the policy/DB bridge. It creates no DB/tables/user/organization/dataset or entitlement and cannot be used to provision them. The verifier's temporary cluster is cleaned up, not left available as an apply target.

### Current capability, not the full Sanity pipeline

- Only already-registered, supported **draft** schemas; no NCW/legacy schema converter or source-published import. Unknown/unsupported/published/media records produce report dispositions, not restored content.
- Strict bounded UTF-8/duplicate-key-aware reader: 32 MiB file, 512 KiB line, 10,000 records; duplicate IDs/unsafe keys/unrepresentable Unicode rejected. Up to **8 MiB retained eligible raw source**; apply accepts **1–100 eligible drafts in one atomic transaction** (identity allocation, revisions/references, CAS, receipt, audit). Structural per-record bounds also apply.
- Strong references must close within eligible input candidates, including forward/cyclic references; unavailable/excluded targets quarantine owning records. Weak missing targets may remain explicit private diagnostics. Assets are unverified, no bytes fetched/uploaded; quarantine is **report-only**, with original source left in place, not a stored recovery workflow. Secret/operational records are excluded.
- Same actor/dataset/snapshot/mapping/schema/candidate fingerprint can replay its receipt after fresh authorization; changed/existing identities conflict rather than overwrite. This is deterministic replay, **not resume/checkpoints/jobs**. Zero eligible drafts fails apply rather than pretending a restore succeeded.
- No persistent quarantine, asset restoration, promotion, releases/outbox, publish, draft delete or complete NCW pipeline. Media mapping/collision/hash/video blockers remain open. Full pipeline completion/full restoration must **not** be claimed.

## 5. Billing timing and release boundary

[Stripe reconciliation](cms-persistence.md#stripe-subscription-events--implemented-not-deployed) adds durable deduplication/canonical state/identity and old-replacement fencing under the persisted account lock. Identity failures do not grant access; DB/provider failures roll back without completion receipt and remain retryable. CMS locks intersect billing writes, but **write lockout is immediate relative to the accepted persisted application-DB state, not the instant Stripe changes during outage/delivery delay**. A previously locked CMS transaction may commit before billing obtains its lock. There is no outage freshness/instant propagation guarantee, no provider fetch on every CMS read, no draft deletion and no deployed reconciliation-scheduler claim.

Separately review/apply the two-table Stripe migration before deploying changed webhook code. Full tests, actual Prisma concurrency/failure checks, browser acceptance, media/release/restore gates and production approval remain required; this runbook is not sign-off.
