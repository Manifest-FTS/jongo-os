## Ownership, IDs and lifecycle

CMS storage IDs and internal FKs are PostgreSQL UUIDs generated with the existing `gen_random_uuid()` convention. Source identities are **TEXT**, never coerced into UUIDs. All new CMS FKs use `ON DELETE RESTRICT ON UPDATE RESTRICT`; no cascade can erase CMS history. Existing columns, rows and migrations are unchanged. The foundation's only existing-table addition is `Site` uniqueness on `(id, organizationId)`, which is already logically unique because `id` is its PK. The separate Stripe tables use provider TEXT identities as described below.

`CmsDataset.organizationId` requires an existing organization. Optional `siteId` is enforced by a composite FK `(siteId, organizationId) -> Site(id, organizationId)`. A null site is a standalone **organization-owned** dataset, not a global dataset. A linked site cannot be reassigned to another organization or hard-deleted while linked. Existing organization deletion cascades may now be blocked by CMS restrict FKs; this is deliberate protection, not a new cascade. Soft deletion must also be checked by services because FKs do not inspect `deletedAt`/`archivedAt`.

Dataset keys are unique on `(organizationId, key, environment)`, independent of site. Names/keys/environments are nonempty, case-sensitive text; no implicit production environment, source tenant mapping or normalization. Dataset provisioning/relinking requires explicit authorization and audit. Never expose a dataset simply because its environment is named production.

## Exact source preservation

- Enforce unique `(datasetId, nativeId)` and `(datasetId, logicalId, variant)`. The extra `(datasetId, id)` key supports compound internal FKs. Document identity fields (`id`, `datasetId`, `nativeId`, `type`, `logicalId`, `variant`) are immutable by SQL trigger.
- For the approved Sanity adapter only, derive `logicalId` by removing **exactly one** leading `drafts.` prefix and classify draft; otherwise retain ID as logical identity and classify published. The DB deliberately does not impose Sanity prefix syntax on future native adapters. Service validates the adapter's bijection; it must never merge type families or derive type from an ID.
- Draft and source-published envelopes are separate rows with separate current revisions. Draft-only remains draft-only. `variant=published` is source/native identity classification, **not editorial approval or permission for public delivery**. Native edits allocate explicit stable TEXT IDs under a reviewed policy; storage UUIDs must not replace source IDs.
- `sourceRev` retains opaque `_rev` unchanged. It is not sequence, `nativeRev`, timestamp or CAS authority. Repeated source revisions across documents are valid; no uniqueness is imposed on source revision strings.
- Source date strings are deliberately TEXT: exact spelling, offset, precision and invalid source values survive. Validate/diagnose before acceptance; never substitute current time. `createdAt` is native revision insertion time; `ingestedAt` is native intake time (both default now, may be explicitly supplied during authorized staging). No source time is used for concurrency ordering.
- `payload` retains the full validated document/AST, including nested `_key`, `_ref`, `_weak`, marks, original slug object, system fields and unknown **safe** fields. Relational projections do not rewrite the source. Unsupported fields require private disposition and block later publication.
- JSONB preserves JSON values, **not source bytes, whitespace, key order, duplicate keys or number lexemes**. For an eligible imported record, persist `sourceRecordRaw` as the exact strictly decoded UTF-8 JSON record text, excluding NDJSON delimiter and any file BOM; `sourceSha256` hashes those exact UTF-8 bytes. Preserve full-file bytes/hash separately in the future import manifest. Reject invalid UTF-8, duplicate keys, embedded NUL/unrepresentable values before persistence; never silently normalize them. Raw text is private and not a rendering input.
- `payloadSha256` uses `jongo-json-sorted-v1`: recursively sorted UTF-16 code-unit object keys, retained array order, JSON number/string encoding and UTF-8 SHA-256, with no Unicode normalization. This is versioned canonicalization, **not RFC 8785** and not the raw-source hash. SQL checks hash shape and raw/hash co-presence, **not hash correctness, raw JSON validity, payload equivalence or source metadata equality**. Native saves compute payload hashes; the bounded importer separately computes raw-record/payload hashes before insertion. Full legacy-converter/source-parity acceptance remains future work.
- Provenance should pin source adapter/project/dataset, snapshot hash, mapping/schema/canonicalization versions and safe source location metadata. It is not an instruction to fetch URLs. Never persist excluded secrets such as `mux.apiKey`, private operational payloads in editorial datasets, or raw records in general logs/audit. Exact retention applies only to explicitly eligible, security-screened records; quarantine storage/import models remain deferred.

Slugs and locales remain nullable. Their compound index is **not unique**: this foundation invents neither locale nor slug, and permits duplicate slugs across variants/types/locales pending a reviewed routing policy. Do not resolve a public route using this index without a later uniqueness/release contract.

## Revisions, references and constraints

`CmsRevision` is append-only: SQL triggers reject all UPDATE/DELETE (including no-op updates) and TRUNCATE. `CmsMutation` has the same protection. Ordinary writes cannot prune history; a future retention/privacy operation needs a separately reviewed migration/privileged maintenance policy. Table owners/superusers can disable triggers, so use a least-privileged runtime DB role, never rely on these guards against a database administrator. SQL-only guards cannot be represented in Prisma: retain the migration, never replace it with `db push`.

Revision uniqueness is `(datasetId, documentId, sequence)` and `(datasetId, nativeRev)`. Sequence starts at 1; positivity/uniqueness are DB-enforced, but monotonic allocation and schema compatibility are service responsibilities. `(datasetId, documentId, id)` permits the document pointer FK `(datasetId, id, currentRevisionId)` to target **only its own revision**, not another document or dataset. Create the envelope with null pointer, append a revision, then CAS the pointer within one transaction. The SQL guards do not by themselves enforce pointer advancement, sequence continuity or lock-version increments.

One `currentRevisionId` per exact variant is intentional. No paired draft/published pointer, release pointer, approval state, unpublish operation or mutable revision payload is invented here. Restore means a **new** revision copied through validation, never updating history. A future publish service cannot merely flip a variant or pointer: it needs an independently reviewed release/approval model.

Reference source FK `(datasetId, sourceRevisionId)` enforces source scope. Target FK `(datasetId, targetDocumentId, sourceRef) -> CmsDocument(datasetId, id, nativeId)` enforces both same dataset **and exact source `_ref` equality**. Empty source refs can only be `invalid`; retain them for explicit diagnostics. `resolved` requires non-null target and nonempty ref; every other state requires null target. Weak unresolved references are allowed; strong unresolved/excluded/invalid references are retained privately and must block affected publication. Cycles/forward refs work by allocating envelopes first, then revisions/edges. Never strip a target prefix to force resolution.

`path` is an RFC 6901 pointer to the reference object (empty string denotes root), including array indices; escape `~`/`/`. Unique `(datasetId, sourceRevisionId, path)` allows repeated targets at different locations. SQL checks root/slash shape only; service verifies escaping, traversal and that the indexed `_ref`/`_weak` actually match payload. Preserve original reference JSON including `_key`. Resolution metadata may change as envelopes arrive; services must not rewrite source identity/path/weak flags or remove findings to hide failures. These derived-index rules are not enforced by revision triggers. A later resolver must audit changes and revalidate publish closure; an index row is not an approval.

There is **no asset table/FK** yet. Source asset records may only be eligible private identity/payload metadata under approved schemas; a resolved document reference does not establish media availability, integrity, approval or publication readiness. Future asset relations must also use dataset-bound composite FKs and `onDelete: Restrict`.

## Implemented dataset access — capacity intersected with tenant role

`resolveDatasetCmsCapabilities(userId, datasetId)` reads the live actor, dataset, organization, actual persisted owner/sponsor, optional site, memberships and unrevoked grant in one `RepeatableRead` transaction. It returns scope/action bits only, not subscription/customer/financial records. Browser execution, malformed UUIDs, a flag other than exact `JONGO_CMS_ENABLED=true`, missing/deleted/archived or inconsistent scope, unknown grant roles and database/schema failures deny all capabilities. The flag **defaults off**.

- Owner and live organization-level admin receive dataset admin role without needing a grant row. A live organization collaborator starts as reader; an explicit live dataset grant can raise that role to editor/publisher/admin, never lower the tenant baseline.
- A site-only member needs an explicit grant for this exact linked dataset. No grant alone replaces a live owner/organization/site relationship; site-only membership grants nothing on a standalone or other site's dataset.
- Role ranks are reader < editor < publisher < admin. Read/export capacity survives sponsor downgrade when tenant access remains valid. Editing requires editor or higher **and** the actual owner's active, unexpired Studio/Scale subscription. Publish requires publisher or higher; dataset/grant management requires admin; customization additionally requires Scale. These are capability bits, **not implemented publish/export/grant-management endpoints**.
- Collaborator purchases, organization receivables, financial `super_admin`, bootstrap email and technical `PlatformAdmin` grants provide **no entitlement, CMS or financial bypass**. Trialing, unknown/inactive/expired subscriptions cannot author. No new membership, grant or paid plan is synthesized.

This resolver is snapshot-based capability inspection, not a reusable write lock or authority cached for a later request. The document service independently applies aligned policy inside its own transaction; a future shared transaction-bound helper must preserve that alignment. The organization-only schema preview still uses its narrower owner-edit policy, not this dataset resolver.

## Implemented private document service — route-enabled drafts only

The Node-only [document module](../apps/web/src/lib/cms/documents.ts) exports `listCmsDocuments`, `getCmsDocument` and `saveCmsDraft`. The organization-only schema preview remains local-only. Calls require authenticated server-supplied `userId`, explicit dataset scope and a separately prepared isolated database/client containing the new models. Missing delegates/tables fail closed; there is no mock or legacy fallback. No configured application database was migrated or provisioned, and no production rollout is authorized.

Reads require exact server-only `JONGO_CMS_ENABLED=true`; every write additionally requires exact `JONGO_CMS_WRITES_ENABLED=true`. Both default off. ### Read and save contracts

- `listCmsDocuments` returns bounded private metadata only, default 50/max 100, UUID keyset `afterId` and optional registered type filter. No payload, raw source, provenance, sponsor or consent is projected. Metadata may describe either variant; that is not public delivery.
- `getCmsDocument` returns only the exact same-dataset, unarchived **draft** and its current revision's `id`, `nativeRev`, `sequence`, `schemaVersion`, `payload`. It exposes no historical/raw/provenance relation; a broken current pointer is unavailable, not a cross-document fallback. This authenticated private payload is not a public-safe DTO.
- `saveCmsDraft` accepts `userId`, `datasetId`, optional storage UUID `documentId`, exact TEXT `sourceId`, `input`, dataset-scoped retry key `mutationId`, and native expectations `expectedNativeRev`/optional `expectedLockVersion`. The retry key maps to `CmsMutation.key`; the service generates the receipt UUID independently. It accepts only nonempty `drafts.` identities; it neither rewrites a published variant nor imports/promotes source records.
- Existing drafts require the exact current `nativeRev`; an optional lock expectation must also match. New drafts require null/absent native expectation and zero/absent lock expectation. Payload `_rev` is never CAS authority. Server registry supplies `schemaVersion`; next sequence is allocated from the highest retained revision, not source tokens or an older pointer.
- Inputs are detached before awaiting, inspected as bounded plain JSON, limited to 512 KiB canonical bytes, 512 UTF-8 bytes for indexed identity/text values, 128 bytes for retry keys, 200 references and 1,024 bytes per reference path. Decoded keys and values reject NUL/unpaired UTF-16 surrogates while preserving valid surrogate pairs and literal backslash-u text. No Unicode normalization or serialized-escape false positives. Structural/schema limits also apply.
- New mutations validate against the current registered draft schema and reject quarantine findings. Consent/review-pending content may be saved privately, without asserting publication approval. Exact same-dataset references are indexed with RFC 6901 paths and registered target-type validation; unresolved strong/weak references remain private findings, not evidence of publish readiness. The separate bounded importer allocates eligible draft identities in two passes; it is not a durable quarantine/staging pipeline.

### Schema-independent retry identity and source preservation

Operation `cms.draft.save.v1` fingerprints canonicalization version, actor, dataset, exact `sourceId`, optional document UUID, normalized optional native/lock expectations and SHA-256 of the **entire detached submitted payload**, including envelope claims. It intentionally excludes mutable server registry/schema versions. After fresh edit authorization and policy locking, an existing `(datasetId, key)` receipt is checked **before current-schema validation**. Same actor/operation/fingerprint returns only the original projected version-1 receipt, even after a schema upgrade/removal or a later edit; it creates no duplicate revision/audit and never moves the pointer backward. Changed payload/envelope/expectation/actor conflicts. Revocation/downgrade denies even an otherwise exact replay. New keys still validate against today's schema.

New native revisions keep source columns null. Submitted `_rev`/`_createdAt`/`_updatedAt` remain payload claims; the original creation envelope is recorded in provenance with `origin: native` and `submittedEnvelopeTrusted: false`, not promoted to verified import metadata. Later edits carry forward the prior revision's `sourceRev`, `sourceCreatedAt`, `sourceUpdatedAt`, exact `sourceRecordRaw`, `sourceSha256` and provenance while stamping the service operation/canonicalization. Edited envelope claims cannot replace those source values or the original untrusted creation envelope. Raw source bytes are not regenerated from the edited payload. Thus retained raw source need not equal a later native payload. The separate importer computes raw and canonical payload hashes before insertion; SQL hash-shape checks alone do not prove fidelity.

### Scoped row locks, CAS and atomic writes

1. Fresh preliminary authorization rejects denied callers **before locks**; it is not final authority. Writes use a new interactive `Serializable` transaction; reads use `RepeatableRead`.
2. Lock order is dataset `FOR UPDATE`; organization `FOR SHARE`; actor/sponsor users sorted by ID `FOR SHARE`; this actor's organization membership; exact dataset grant; optional site and this actor's site membership `FOR SHARE`. Fixed SQL identifiers and parameterized values target scoped rows, not policy-table locks. Existing revoked/deleted membership/grant rows are included by the locking queries. Policy is re-resolved after locks and before receipt lookup; standalone datasets skip site locks. Existing draft rows are then locked `FOR UPDATE` by dataset + document UUID.
3. Existing policy rows block conflicting UPDATE/DELETE until commit. Absent rows cannot be row-locked; serializable predicate reads and fresh retries handle conflicts. External policy writers may use another lock order and deadlock; do not infer full webhook/role-writer correctness from the lock protocol alone. No provider/network request occurs inside this transaction.
4. SQL lock timeout is 2s and statement timeout 8s; Prisma `maxWait` is 3s and transaction timeout 10s. At most **three total attempts** retry `P2034`, `P2002` or raw `P2010` SQLSTATE `40001`/`40P01`. Every attempt starts a fresh transaction and reauthorizes, including replay. Exhausted retryable failures become conflict; other database failures become sanitized unavailable errors. No query continues inside an aborted transaction.
5. Insert a **final immutable receipt**, append the linked immutable revision/reference rows, then CAS the scoped draft pointer with current pointer + lockVersion and increment lockVersion. Exactly one updated row is required. Insert redacted organization-bound `AuditLog` in that same transaction. Any receipt/revision/edge/CAS/audit failure rolls back all writes; no pending success receipt survives. The returned receipt has only `version`, dataset/document IDs, exact `nativeId`, revision ID, `nativeRev`, sequence and lockVersion. Errors are `denied`, `conflict`, `invalid`, `unavailable`; raw SQL/private content is not logged or returned.

Dataset provisioning/relink/archive, grant mutation, restore/delete, publish/unpublish and release/outbox workflows remain separate unimplemented operations. Their future writes must use equally fresh guards and atomic scoped audit. Existing receipts are retained; no pruning policy is implemented.

This is a database foundation, **not DB row-level authorization**. No RLS or security-definer mutation API is installed. Every Prisma repository query must carry server-resolved dataset scope. SQL checks supplement, not replace, guards/runtime schema validation/audit. `updatedAt` follows existing Prisma `@updatedAt` behavior (no SQL default); handwritten SQL writers must supply it.

## Bounded importer — current persistence contract

The [CLI](../scripts/import-sanity-ndjson.ts) defaults to no-DB dry-run: it imports only the planner, validates UUID syntax and reads the selected file, not live actor/dataset authority. Explicit apply uses [local target validation](../apps/web/src/lib/cms/import/local-database.ts) and the same guarded `withCmsWriteTransaction` as native editing. It requires both flags, matching confirmation, fresh tenant/editor/sponsor policy and a verified disposable local database. Exact parser/options and commands are in the [runbook](cms-local-verification.md#3-importer--no-db-dry-run-by-default).

Mapping `registered-drafts-v1` accepts only supported registered **draft** envelopes. Reader bounds are 32 MiB/file, 512 KiB/line and 10,000 records; planning retains at most 8 MiB eligible raw source. Apply rejects more than 100 eligible drafts and zero eligible drafts. It allocates all eligible exact identities first, then immutable revisions/reference edges, pointer CAS, receipt and scoped audit in **one transaction**. Existing exact IDs conflict rather than overwrite. Source raw text/hash/revision/date text and AST are preserved; native revisions remain independent. Strong-reference closure uses only this file's eligible candidates; missing/excluded strong targets quarantine owners, while allowable unresolved weak edges remain private diagnostics. No existing-DB-target resolution is promised.

The receipt key derives from dataset + snapshot hash; fingerprint additionally pins actor, mapping, schema descriptors and candidate checksums. Freshly authorized exact replay is a no-op (`replayed: true`, no new applied rows); changed identity/body/schema conflicts. This is **not resumable jobs/checkpoints**. Quarantine is redacted reason/count reporting only, not a persisted recoverable store. Original private source stays in place; assets are unverified/report-only, secret/operational types excluded. No full legacy/NCW converter, media upload, promotion, release/outbox, public delivery or full restoration exists.

## Stripe subscription events — implemented, not deployed

The separate [migration](../prisma/migrations/20261019160000_stripe_subscription_events/migration.sql) adds exactly **`StripeSubscriptionEvent`** (unique `eventId` completion/outcome ledger) and **`StripeSubscriptionState`** (subscription identity/watermark/terminal state). It changes no existing subscription values/products/prices. **Review and apply this migration before deploying the new webhook code**, with compatible client generation and separately approved target/backups. Neither it nor CMS foundation has been applied to a configured application DB by this work. This guide supplies no production migration command.

After bounded raw-body signature verification, the [webhook](../apps/web/src/app/api/billing/webhook/route.ts) retains domain-order handling and routes subscription events to [reconciliation](../apps/web/src/lib/billing/subscription-events.ts):

- Resolve the account by persisted Stripe customer, lock that `User` row `FOR UPDATE`, deduplicate and recheck live user/customer/subscription/optional metadata identity. Canonical provider retrieval stays **inside** that lock (8s timeout, no network retries per retrieval). CMS writes hold sponsor `FOR SHARE`, so the billing update conflicts with their authorization locks. No Stripe call is made per CMS content read.
- Do not trust incoming upgrade payloads or event timestamp ordering for grants. Older/equal-time deliveries reconcile canonical current state; event time is an audit watermark, not a reason to skip an authoritative downgrade. Missing plan metadata clears entitlement rather than retaining advanced capacity. Unknown plans/statuses fail CMS policy closed.
- Ignore obsolete non-checkout subscription identities and terminal subscriptions. Replacement checkout B can replace bound A only after proving A terminal (`canceled`/`incomplete_expired`) through its matching ledger or canonical lookup and proving B's provider creation is strictly newer. Foreign identities fail closed; old A cannot resurrect after replacement. A 404 on A during replacement is not cancellation proof. Only a signed deletion for the bound canceled subscription permits the narrow missing-resource tombstone fallback.
- Account/state/completion commit atomically. DB/provider failures roll back and surface HTTP 500 without a completion receipt so delivery can retry. Identity mismatches/obsolete events may be durably acknowledged as non-applied outcomes; acknowledgement is not an entitlement grant.

**Timing limit:** fresh CMS writes lock out once a downgrade/cancellation event is accepted and persisted in the application DB (or the stored period expires), not instantly when Stripe changes. A write already holding the policy lock may finish before billing obtains its lock. During webhook/provider outage persisted state may lag; no instant propagation/outage freshness guarantee or deployed reconciliation scheduler is claimed. Drafts are retained, never deleted on downgrade. Serialized billing test doubles plus direct SQL lock checks are not real provider/Prisma concurrency acceptance.
