# Craft / Golf Lab initial preview

## Whole-site content and CraftStructure — preview.19

Every section of the one-page Golf Lab site is now a fixed (singleton) Craft document the public page reads by id: hero, the facility, membership (plans, prices, benefits), technology (copy, slideshow images, data highlights), how it works, instructors (people, photos, profile text, lesson links), booking, FAQ (answers keep their links), find us (map listing, directions link), partners (names, links, logos), site settings (logo, menu, tagline, contact, address, social, membership and booking links) and search and sharing (page title, descriptions, keywords). Images are chosen from the shipped library or uploads; delivery resolves a chosen image to its address (shipped file, or an https address inside the configured media store) and falls back per field to the built-in copy. The studio seed documents are the built-in copy, narrowed by the same rules as published ones.

`craftStructure` (exported from `@jongo/craft`) is the menu, the counterpart of Sanity's Desk Structure: `craftStructure.define([...], schemas)` with `group`, `document` (a fixed document, opened directly with no list beside it), `documents` (the list of a type) and `divider`. Without one the studio lists each type, as before. The Golf Lab menu is "Homepage" (the sections in page order) and "Site". `/craft` opens the first entry.

Existing databases: `npm run craft:seed -- --fill --publish` creates the new documents and fills fields a stored document lacks (never changes a value that is there); `--publish` publishes what it created and what it filled when that document was already published. The earlier `homepage` document (`home`) is no longer part of the content model and is ignored.

No Jongo role changes were needed: Jongo super admins and admins already enter every app's Craft as admin (editing and publishing); other team members need an editor or publisher grant on the app.

## Studio persistence adapter and Golf Lab wiring — preview.9, 2026-11-04

**Status: implemented and tested locally; a preview, not production-ready.** Nothing in this change was run against the real Coolify database (the website's local `.env.local` points `JONGO_CRAFT_DATABASE_URL` at a Coolify-internal host that is unreachable from the development machine; no test or script used it). No commits, pushes, deployments, provider or network calls.

**Env rename (2026-11-05).** The Golf Lab website now reads `JONGO_CRAFT_DATABASE_URL`, `JONGO_CRAFT_DATASET`, `JONGO_CRAFT_STUDIO_PASSWORD`, `JONGO_CRAFT_SESSION_SECRET`, `JONGO_CRAFT_ALLOW_REMOTE_DB`, `JONGO_CRAFT_DELIVERY_ENABLED` and `JONGO_CRAFT_DELIVERY_REVALIDATE_SECONDS`. The old names (`DATABASE_URL`, `CRAFT_DATASET`, `CRAFT_STUDIO_PASSWORD`, `CRAFT_SESSION_SECRET`, `CRAFT_ALLOW_REMOTE_DB`, `CRAFT_DELIVERY_*`) are no longer read and there is no fallback: a host that only has the old names runs in local-draft mode with delivery off (fail-closed). `CRAFT_PREVIEW_ENABLED` is unchanged because it also gates the website's `/admin` and `/portal` previews. The text below uses the new names.

**What it does.** The `/craft` content studio of `dd-thegolflab` can now save to the PostgreSQL persistence layer (`@jongo/craft/server`, preview.8) instead of page memory, behind a TEMPORARY studio login. Editors see per-document state (Saved, Unsaved changes, Saving, Conflict, Error) and a visible **Published** or **Draft** status, and can Save a draft, Publish, Unpublish and Discard a draft. When the database or the login settings are missing the studio opens in clearly labeled **LOCAL DRAFT MODE** (page memory only, names of the missing settings shown, nothing written anywhere).

**What it does NOT do.** The public homepage still renders hard-coded copy, so Studio edits (even published ones) do **not** change the live site yet; a delivery step that reads published documents is still to be built. No media/image uploads (images can only be picked from the assets listed in `craft-content.ts`). The login is a shared-password stopgap, not user accounts, roles or auditing of individuals (rows record an opaque per-session actor). The studio cannot create new documents (only the seeded ones are editable), has no revision history view, no real-time collaboration and no import/export UI. Backups are handled at Coolify/Jongo level, not by Craft.

### Studio adapter (`jongo/craft`, UI only)

`ContentStudio` gained an optional `store` prop (type `StudioStore`, with `StudioRecord`, `StudioFailure`, `StudioResult`, `StudioDocSummary` and `MutationKeys` exported; the pure parts are also in `@jongo/craft/content`). Without `store` the Studio behaves exactly as before (local drafts, existing wording and tests). With a store: `list`, `load`, `saveDraft`, `publish`, `unpublish`, `discardDraft`, each returning `{ ok: true, ... }` or `{ ok: false, code: 'conflict' | 'invalid' | 'denied' | 'unavailable', message, fieldErrors? }`. The store is the only boundary the browser sees; the component imports no server code, `pg` or `groq-js` (the client-entry import-graph test still passes and now covers the new modules).

- *Optimistic concurrency.* Every mutation sends the revision and lock version the editor loaded. A `conflict` keeps the editor's text on screen, says plainly that it was not saved, and offers **Reload latest** (which discards the unsaved edits). The Studio never retries with a newer revision by itself, so it cannot silently overwrite.
- *Retry-safe mutation keys.* A key is generated per attempt and is identical for an immediate retry of the same request (same operation, document, precondition and body; key order irrelevant). Any change, or a confirmed outcome, makes a new key. After a lost response the same button retries safely; the server replays the stored receipt.
- *Rules.* Save draft is enabled only when there are unsaved edits (and no conflict is pending); Publish is enabled whenever the document passes the checks and there is something to publish (a draft, saved or not, or a published document with unsaved edits). With unsaved edits Publish is **Save then Publish as one action** (preview.16): it saves with the existing compare-and-set and mutation key, stops on a failure or conflict and shows the usual problem panel without publishing, and otherwise publishes the new revision with its own key and announces "Saved and published." After a lost response the same button retries with the same keys. When Publish is disabled the reason is visible text beside the buttons (and a tooltip and `aria-describedby`): "Published, up to date", "Fix N issue(s) to publish" (a link to the first issue) or "Reload latest to continue" (after a conflict, when every write would conflict again). Unpublish needs a published version; Discard draft needs a draft over a published version that differs from it. Fields are inert while an operation runs. Focus is restored to the pressed button afterwards. A polite live region announces results and an `role="alert"` region shows problems.

  Action matrix (connected mode; server permissions are authoritative, the interface only mirrors them). "-" = not shown.

  | State | Save draft | Publish | Unpublish | Discard draft | Duplicate | Delete |
  |---|---|---|---|---|---|---|
  | Draft, clean, valid | disabled | enabled | - | - | enabled | enabled |
  | Draft, unsaved edits, valid | enabled | enabled (saves first) | - | - | disabled until saved or reset | enabled |
  | Draft, any issues | enabled if edited | disabled, "Fix N issue(s) to publish" | - | - | as above | enabled |
  | Published, clean | disabled | disabled, "Published, up to date" | enabled | - | enabled | enabled |
  | Published, unsaved edits | enabled | enabled (saves first) | disabled until saved or reset | - | disabled until saved or reset | enabled |
  | Draft over published (differs) | disabled if clean | enabled | enabled (keeps the draft) | enabled | enabled | enabled |
  | Draft identical to published | disabled | enabled (clears the draft) | enabled | - | enabled | enabled |
  | Conflict pending | disabled | disabled, "Reload latest to continue" | disabled | disabled | disabled | disabled |
  | Busy | disabled | disabled | disabled | disabled | disabled | disabled |
  | Editor (write, no publish) | as above | - | - | enabled when applicable | as above | - (view note: "You can edit and save drafts...") |
  | Reader | - | - | - | - | - | - (view-only note, fields inert) |

  Fixed (singleton) documents never offer Duplicate or Delete (the server refuses them too); the header tools menu says "Fixed page content: can't be duplicated or deleted". In **local draft mode** (no database) the same set is shown honestly: Save local draft, a disabled Publish with the visible reason "Publishing needs the Jongo Craft database", and a menu with Reset changes, Revert to original snapshot and disabled Duplicate and Delete ("Needs the Jongo Craft database"); Unpublish and Discard draft are omitted because they have no meaning there.
- *Props.* `initial` (server-prefetched list/record or a prefetch failure, shown as an unavailable state with a retry), `notice` (one honest line, both modes), `topbarSlot` (sign-out form), `signInHref` (shown on `denied`). The old "persistence and publishing are not connected" text is dropped only when a store is connected.

### Website server layer (`dd-thegolflab/src/lib/craft/*`, `src/app/craft/*`)

- `db.ts`: lazy `pg.Pool` singleton on `globalThis` (HMR-safe), max 5, idle 30 s, connect timeout 5 s, typed `CraftNotConfiguredError` without `JONGO_CRAFT_DATABASE_URL`; the URL is never logged. `server-only`; never imported from client code (tested).
- `config.ts`: persistence is enabled only when `JONGO_CRAFT_DATABASE_URL`, `JONGO_CRAFT_STUDIO_PASSWORD` (>= 12 chars) and `JONGO_CRAFT_SESSION_SECRET` (>= 32 chars) are all valid and `JONGO_CRAFT_DATASET` (default `production`) is a valid name. Anything missing fails closed (local mode / disabled login) and only NAMES are reported.
- `session.ts`: stateless token `v1.<payload>.<signature>`; payload has a random 192-bit session id, issue time and expiry (8 h); HMAC-SHA256 signature compared with `timingSafeEqual`; expiry, clock skew and maximum lifetime enforced. Password comparison hashes both sides (SHA-256) and uses `timingSafeEqual` on the equal-length digests. Cookie `craft_studio_session`: `httpOnly`, `Secure` in production, `SameSite=Strict`, `Path=/craft`, 8 h. Logout clears the cookie and remembers the session id in memory until it would expire (best effort, see limits).
- `rate-limit.ts`: failures only; 5 per client address and 30 global per 15 minutes block further attempts (even a correct password) with a retry time; each failure also earns a doubling delay (250 ms up to 4 s). In memory, **per server instance** (a second instance or a restart has its own counters). The client address is the right-most `X-Forwarded-For` entry (the one our own proxy appended), used for throttling only.
- *CSRF.* Layers: (1) Next.js rejects a Server Action POST whose `Origin` does not match `Host`/`X-Forwarded-Host` (`serverActions.allowedOrigins` is not configured); (2) the session cookie is `SameSite=Strict` and is the only credential accepted (never a header or body value); (3) our own `isSameOriginRequest` in every action and in login/logout: `Origin` must be present and equal the host, and `Sec-Fetch-Site`, when present, must be `same-origin`. Next lets a request with no `Origin` through; ours refuses it (tested over HTTP).
- `service.ts`: builds the registry from `craft-content.ts`, the authorize callback (a valid session may do `read`, `read-drafts`, `write`, `publish` on the configured dataset only; `import`, every `export*`, `admin` and other datasets are denied; no session denies everything), ensures the dataset exists once with an internal admin context (not reachable from the browser) and exposes list/load/save/publish/unpublish/discard returning Studio results. Input is validated before any database access. It takes the session as an argument, so it is tested without Next.
- `src/app/craft/actions.ts` (`'use server'`): each action re-checks the exact preview flag, persistence enabled, same-origin and the session, validates shape and size (document id pattern, revision/lock/mutation-key shape, plain JSON only, depth 32, 20,000 nodes, 512 KiB, no `__proto__`/`constructor`/`prototype`, registered `_type` only, a revision is mandatory so documents cannot be created) and maps every error to `conflict`/`invalid`/`denied`/`unavailable` with fixed messages: no SQL, driver text, stack or document content. Returns only `doc`, revision, lock version, variant and the published revision, not sequence numbers, receipt flags or internal ids.
- *Pages.* `/craft` (catch-all): exact `CRAFT_PREVIEW_ENABLED === 'true'` gate and noindex as before; persistence on plus valid session renders the connected studio (first paint prefetched); persistence on without a session redirects to `/craft/login`; persistence off renders the local studio with a notice naming the missing settings. A database outage becomes an "Storage unavailable" state with a retry, never an error page. `/craft/login`: same gate (404 otherwise) and noindex, neutral Jongo styling; when persistence is off it shows the disabled state and names instead of a form.
- *Scripts (not automatic; the app never migrates on boot).* `npm run craft:migrate` (`scripts/craft-migrate.mjs`, `runMigrations`) and `npm run craft:seed` (`scripts/craft-seed.mjs`: creates DRAFTS for the documents in `craft-content.ts` only where missing, resolving references in passes, never overwrites, prints counts). Both read `process.env` only (no `.env` file is loaded; for a local database export `JONGO_CRAFT_DATABASE_URL` in the shell), exit non-zero on failure, never print the URL, and **refuse a non-loopback database host unless `NODE_ENV` is `production` (the deployed app container) or `JONGO_CRAFT_ALLOW_REMOTE_DB` is exactly `true`** (exit 2; a `host=`/`hostaddr=` URL parameter counts as remote). `craft:seed` loads the TypeScript content module with the `typescript` package (a devDependency) and writes a temporary directory under `node_modules/.cache`; both must be available where it runs.
- *Dependencies.* `pg` and `groq-js` added to `dependencies`, `"engines": { "node": ">=22.12" }` (groq-js 2.x). `@jongo/craft` is vendored as `vendor/jongo-craft-0.1.0-preview.9.tgz` via `npm run craft:repack` (older tarballs kept).

### Operator runbook (Coolify)

1. *Database.* Create a separate PostgreSQL database for Craft. Run migrations as the owner role and the application as a least-privilege role (grants in the "Server persistence" section below).
2. *Environment names* (Coolify application environment; values never in git): `CRAFT_PREVIEW_ENABLED=true` (only on an approved isolated preview host), `JONGO_CRAFT_DATABASE_URL`, `JONGO_CRAFT_DATASET` (optional, default `production`), `JONGO_CRAFT_STUDIO_PASSWORD` (>= 12 chars), `JONGO_CRAFT_SESSION_SECRET` (>= 32 chars; generate with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`). In the Coolify app container `NODE_ENV` is `production`, so `npm run craft:migrate` and `npm run craft:seed` run as they are and the internal database host needs no flag. `JONGO_CRAFT_ALLOW_REMOTE_DB=true` is only for a developer machine that deliberately targets a remote database (for example through a tunnel on a non-loopback address); never set it in the app's environment.
3. *Migrate and seed.* Run `npm run craft:migrate` then `npm run craft:seed`, either as a Coolify pre-deployment or post-deployment command, or manually in the application's terminal. (The exact setting name and where it appears varies by Coolify version; verify it in the dashboard. Whether `node_modules` including `typescript` and a writable `node_modules/.cache` exist at that point depends on the Nixpacks build output and is unverified.) Both are idempotent. A post-deploy run happens after the new code starts, a pre-deploy run before; the seed is safe either way.
4. *Rotation.* Changing `JONGO_CRAFT_STUDIO_PASSWORD` stops new sign-ins with the old password but does **not** end sessions already issued. Changing `JONGO_CRAFT_SESSION_SECRET` invalidates every session immediately (everyone must sign in again). Rotate both after a suspected leak. Restart/redeploy to pick up changed environment values.
5. *Node version.* `engines.node >= 22.12` is declared because groq-js 2.x needs it. Nixpacks reads `engines`, but which Node version Coolify's build actually selects is **to be verified** on the first build.

### Security decisions and limits

Decisions: fail closed on any missing/short setting; exact-`true` preview gate on every route and action (login 404 otherwise); signed httpOnly/Strict/path-scoped cookie; constant-time comparisons; no secret or URL in logs, HTML or errors (asserted); allowlist authorization instead of a role system; bounded payloads; compare-and-set plus idempotency keys end to end; the migration role is kept apart from the application role. Limits: shared password (no individual accountability, no MFA, no lockout beyond the throttle); throttle, logout revocation and the singleton pool are per process; stateless tokens cannot be revoked across instances or restarts except by rotating the secret; `Secure` cookies need HTTPS (Coolify terminates TLS); the throttle trusts the proxy's `X-Forwarded-For` and treats every caller without one as one address; the body limit is Next's default 1 MB (documents are capped at 512 KiB); `list` reads at most 100 documents and fetches titles one by one (fine for five documents, not a design for thousands); published content is stored but nothing delivers it; no audit UI. This is a STOPGAP to be replaced by real user authentication before any wider use.

## Server persistence — preview.8, 2026-11-04

**What it is.** `@jongo/craft/server` (a server-only subpath of the existing `@jongo/craft` package, brand "Craft"; no second package) is a standalone, single-tenant PostgreSQL persistence layer so the Golf Lab can run Craft against its **own isolated database** without the multi-tenant Jongo platform. It has no Organization/User/Stripe/subscription/entitlement tables or concepts. The host supplies identity (an opaque `actorId`) and authorization (a required, fail-closed `authorize(actorId, action, datasetName)` callback). Preview quality: it has been exercised only by the tests below, never against production data or a deployed Golf Lab database, and **no production-readiness claim is made**.

**Scope of this change.** Only `jongo/craft/**` and this file. Not touched: `dd-thegolflab`, `jongo/apps/**`, `jongo/prisma/**`, `jongo/docs/cms-*.md`, legacy repositories. No commits, pushes, deployments, secrets/env reads or provider/network calls. The GROQ query engine, privacy stripping and NDJSON export/import were **copied and adapted** from `apps/web/src/lib/cms/{query,export,import}`; that duplication is a known follow-up (dedupe once both sides settle). The database schema ports the ideas of the `20261019120000_cms_persistence_foundation` migration into a self-contained `craft` schema.

**Install and wiring** (full examples in `craft/README.md`): `npm i @jongo/craft pg groq-js`. `pg` and `groq-js` are *optional* peer dependencies (dev dependencies here); UI-only consumers need neither, and the client entries never reach the server code (tested by scanning the import graph; also verified with a real `npm pack` extraction where `@jongo/craft` imports without `pg`/`groq-js` installed and `runGroq` fails with `dependency_missing`). `groq-js` ^2 needs **Node >= 22.12**; it is loaded lazily inside the query function only. Craft reads **nothing from the environment**: the host owns `JONGO_CRAFT_DATABASE_URL` and passes a `pg.Pool` through `createPgExecutor(pool)` (a two-method `SqlExecutor` interface, `query` and `transaction`; Craft never imports `pg`). All SQL is parameterized with fixed identifiers.

**Deploy start.** `await runMigrations(executor)`. SQL lives in `craft/migrations/*.sql` (shipped via the `files` list; `migrationsDir` is a path helper that resolves next to the installed `dist`, so no copy step is needed: `npm run build` emits `dist/server/**` and `npm pack` lists `migrations/0001_init.sql`). Everything is created in the dedicated `craft` schema. The runner records checksums in `craft.schema_migrations` (line endings normalized), runs each migration in its own transaction under `pg_advisory_xact_lock` (transaction-scoped, so it cannot leak across pooled connections; concurrent runners serialize and are idempotent), and refuses to continue when an applied migration's checksum changed (`migration_checksum_mismatch`) or its file is missing (`migration_missing`).

**Tables** (`craft.`): `datasets`; `documents` (uuid pk, `native_id` exact source `_id` including the `drafts.` prefix, `type`, `logical_id`, `variant` draft|published, `current_revision_id`, `lock_version`, archived_at; unique `(dataset_id, native_id)` and `(dataset_id, logical_id, variant)`; composite same-dataset foreign keys; identity immutable; no DELETE/TRUNCATE); `revisions` (append-only; JSONB object payload without the envelope, `payload_sha256`, `native_rev`, `sequence`, `schema_version`, `actor_id`; unique `(document_id, sequence)` and `(dataset_id, native_rev)`; 1 MiB DB cap, 512 KiB canonical service cap); `mutations` (idempotency receipts, immutable); `audit_log` (append-only, bounded detail, no content); `references` (per-revision reference index, populated on save/publish/import). `ON DELETE RESTRICT` everywhere, CHECKs for variant, `sequence > 0`, sha256 shape, object payloads and sizes.

**Immutability limits.** Append-only is enforced by triggers. They stop every ordinary role, including one with full table privileges (tested), but **a superuser or the table owner can disable them** (`ALTER TABLE ... DISABLE TRIGGER`, `session_replication_role = replica`; also tested). Run the application as a least-privilege role and keep the migration/owner role out of the application. Not applied automatically; this exact snippet is what the end-to-end test runs the service under:

```sql
-- run once, as the database owner; the application connects as craft_app, migrations run as the owner
CREATE ROLE craft_app LOGIN PASSWORD '<generate-and-store-in-the-host-secret-store>' NOSUPERUSER NOCREATEDB NOCREATEROLE;
GRANT CONNECT ON DATABASE <database> TO craft_app;
GRANT USAGE ON SCHEMA craft TO craft_app;
GRANT SELECT, INSERT ON craft.datasets, craft.revisions, craft.mutations, craft.audit_log, craft."references" TO craft_app;
GRANT SELECT, INSERT, UPDATE ON craft.documents TO craft_app;  -- no DELETE, no TRUNCATE, no DDL
```

Run `runMigrations` with the owner role (it needs to create the `craft` schema), and re-run the grants after a migration that adds tables.

**Service API and safety.** `createDataset`/`getDataset` (`admin`); `saveDraft` (`write`), `publishDocument`/`unpublishDocument` (`publish`), `discardDraft` (`write`); `getDocument`/`listDocuments` (`read` for the published perspective, `read-drafts` for previewDrafts/raw or the `editor` consumer, which is the only one that sees private fields; list never returns payloads and uses keyset pagination); `queryDataset`; `exportNdjson` (`export`, plus `export-private` for `includePrivate`, plus `read-drafts` for non-published perspectives); `importNdjson` (`import`). The host is asked before any database access or input inspection, and every failure of `authorize` denies. Validation uses Craft's own `validateDocument` against the supplied registry (errors block; `publishRequired` blocks publish only), references resolve against live documents of the dataset plus host-supplied `assets`. Content safety: 512 KiB canonical payloads, depth/nodes/array/property/string bounds, NUL/lone-surrogate/`__proto__`/`constructor`/`prototype` rejected at any depth, bounded actor id (128) and mutation key (128, `[A-Za-z0-9._:/@+=~-]`) lengths, typed `CraftError`s with fixed messages (no SQL, driver text or content), a `redact` helper for audit detail.

**Decisions made (please review).**

1. *Publish.* Sanity-like and deliberately simple: publish writes a NEW published revision (a byte-identical payload copy) and **soft-archives the draft row**. After publishing only the published variant is live, so draft equals published. A later `saveDraft` un-archives the draft (new revision, based on the published `_rev`); `discardDraft` archives the draft and is allowed only while a live published variant exists; `unpublishDocument` archives the published row and restores a draft from the published payload (an existing live draft is kept untouched). Nothing is ever hard-deleted, and every transition is compare-and-set, audited and receipted. Consequence: there is no "unpublished changes" marker other than a live draft row existing next to the published row.
2. *Compare-and-set.* The head is the live draft, else the live published row. Changing an existing document requires `expectedNativeRev` and/or `expectedLockVersion` (`precondition_required` otherwise); a new document must not supply a non-zero expectation. Writers of one logical id serialize through row locks taken in a fixed order, after a per-mutation-key advisory lock so a concurrent duplicate waits and then replays instead of failing.
3. *Import atomicity.* Dry-run reports; apply is **all-or-nothing** when any document is `invalid` or `conflict`: nothing is written, no receipt is stored (the same key can be retried with a fixed file), one `import.blocked` audit row is written and the report is returned with `blocked: true`. Intentional skips (asset documents, `system.*`/`sanity.*` types, `versions.*`, existing ids with `onConflict: 'skip'`) never block. Nothing is overwritten and nothing is coerced. Imported documents get a new `_rev`; well-formed `_createdAt`/`_updatedAt` are kept.
4. *Assets.* Asset documents and binaries are not stored. Asset documents inside an imported file, and `assets` passed by the host, only satisfy reference validation, so image references can dangle until the host's media store exists.
5. *Secret-looking keys.* Export drops properties whose name matches a secret heuristic (including the declared field name `secretCode`) even with `includePrivate`; a round trip therefore loses such fields. Name private fields differently or accept the loss.
6. *Receipts.* Every write, including `importNdjson` apply, needs a `mutationKey`; replay of an import returns the stored summary with an empty report.
